## Pilot — 自研 ROM 系统级手机 Agent（工程落地）

老板选型：自研 ROM 路线（三条路里权限最全的一条）。

### 交付物（D:/phone agent）
- 完整可编译 Android 工程：Kotlin + Compose，包名 `com.pilot.agent`，minSdk 30 / compileSdk 35，AGP 8.7.3 + Gradle 8.11.1。
- `assembleDebug` 与 `assembleRelease`（R8 + lintVital）均通过。Release APK 2.2 MB，Debug 23 MB。
- 源码分层：`perception/`（UiNode + ScreenReader）、`action/`（DeviceActions）、`agent/`（AgentAction / Planner / HeuristicPlanner / CloudPlanner / PlannerRouter / AgentLoop / SkillStore / Guard）、`appfunction/`（AppFunctionBridge）、`service/`、`runtime/`、`ui/`。
- `rom/`：privapp-permissions 白名单、Android.bp（android_app_import + platform 签名）、device.mk、助理 RRO overlay、SettingsProvider defaults、集成指南 README。

### 关键技术决策（以后别推翻，除非有更好理由）
1. **感知节点树优先，截图兜底**。节点树压平 800~1500 token，截图进 VLM 是几千 token + 秒级延迟。
2. **动作协议用单一 data class**，不用 sealed class——模型多吐字段时 sealed 会整体反序列化失败。
3. **护栏（Guard）独立于 Planner**，按目标节点文本判风险，坐标点击才扫全屏（否则微信首页有"支付"入口就天天误报）。
4. **技能库存语义步骤（文本/viewId），不存节点 id**——id 是快照内临时索引，下次必失效。
5. **事件总线放 AgentRuntime 而非 AgentLoop**——服务重连会重建 loop，UI 订阅不能跟着断。
6. **AppFunctionBridge 不做反射硬调**。平台 API 仍 experimental，方法签名跨版本变过，硬编码会静默失效。

### 环境信息
- JDK 17.0.21 在 `D:/Android/jdk-17`（PATH 里没有，必须显式 JAVA_HOME）。
- Gradle 8.14.6 在 `D:/Android/gradle`；项目 wrapper 用 8.11.1（本地有缓存）。
- SDK 在 `D:/Android/Sdk`，platforms 34/35/36，build-tools 34/35。
- adb 37.0.1 在 `C:/Users/zhrl5/platform-tools`。**当前没有连接设备，也没有模拟器镜像**，未上机验证。

### 关键坑（已写进 README）
1. `OfflineRecognizer(assetManager = null)` 必须 null，否则 **native abort**，Kotlin catch 不到

5. Git Bash 调 adb 必须 `export MSYS_NO_PATHCONV=1`，否则 `/data/local/tmp` 被改写成 Windows 路径

### 前一轮测试抓出的真实 bug（都已修）

- 感知层只抓 clickable 节点，文本在被过滤的子节点里 → 加 `labelOf()` 子树聚合

- `ruleBackIfStuck` 误判「无进展」→ 删除，死循环检测改成带屏幕指纹
- 中文别名解析不到英文 label（"设置" vs "Settings"）→ 加 `ALIASES` 表

### 关键实现点
- `openShortcut` 必须先 `resolveActivity` 探测，没有 Activity 就返回 false 让上层回退——不探测的话会误判成功

- 直达成功过一次就判完成（`history` 里找 `直达 ... ok`），否则会重复发同一个 Intent 到死循环（实测「打开电池」连发 3 次）
- 直达失败过就不再试（找 `直达 ... fail`）

### ★ 厂商劫持 action（重要认知）

```
ACTION_POWER_USAGE_SUMMARY       → 节电助手（本该是电池用量）
```

- cookie 注入通道：`adb shell am broadcast --es set_netease_cookie "..."`

### ★ -460 的真实原因（我一开始判断错了）

**先说错的那次**：看到服务端 curl 也返回 -460，就归因成「IP 频率风控」。这个推理只覆盖
一条路径，跑偏了。老板让我查代码逻辑，才发现是**四个 bug 叠加**：

| # | Bug | 表现 | 修法 |
|---|---|---|---|
| 1 | 用 `/song/url/v1` | 恒定 `-460 网络环境存在风险` | 换旧接口 `/song/url` |
| 2 | cookie 塞 URL 参数（2022 字符） | 请求行过长被截断，服务端当未登录 | 改 `Cookie` header |
| 3 | 只试搜索第一首 | 首选常是翻唱版，`url: null` | 遍历前 5 个候选 |
| 4 | 播放 CDN 是 http 明文 | `MediaPlayer what=1 extra=-2147483648` | 放行 `*.music.126.net` |

**修完能出声了。** 第 4 条最难查：报 `MEDIA_ERROR_UNKNOWN`，日志里完全看不出是网络策略拦的。

**方法论教训**：排查时不能只测一条路径。要同时对比「新接口 vs 旧接口」「header vs query」
「第一首 vs 遍历」。四个变量同时坏时，现象看起来就像整条链路被风控。

### QueryEngine（新架构层）
第三类能力，和「操作」「系统直调」并列：
